## 二、数据缺口对账（核心）

demo 用到的字段 vs 后端现状。**结论：数据在库里都有，只是 `read-graph.ts` 没查出来。**

| demo 字段 | 后端现状 | 库里能否提供 | 处置 |
|---|---|---|---|
| `nodes[].degree` | ✅ 有，但**全库口径** | ✅ | 保留；前端另算 `subDegree` |
| `nodes[].influence` | ❌ 无 | ✅ 可算 | **纯前端派生**，不入后端 |
| `edges[].ev`（证据条数） | ❌ 无 | ✅ `evidence_spans` 一对多 | 后端 `count` |
| `evidence[edgeId]`（多条原文） | ⚠️ **只留首条** | ✅ 表里有多条 | 后端改为**数组** |
| `chapters[].title` | ❌ 只给 `chapterCount` | ✅ `chapters.title` | 后端补数组 |
| `codes[].n`（全库计数） | ⚠️ 只有 `legend`（按 cat 聚合） | ✅ | 后端补按 code |
| `exclusiveHits`（关系特异） | ❌ 完全没算 | ✅ 可由边推出 | **纯前端算** |
| `dupGroups` | ❌ 无（demo 里也是空 `[]`） | — | **不做** |

**关键判断：8 项里只有 4 项真需要改后端**（多条证据、章节标题、按码计数、证据条数）。
`influence` / `exclusiveHits` / `subDegree` 都是**纯前端派生**，不该塞进后端。

## 三、后端扩展方案（第一批）

**只增字段、不改语义** —— 现有 `GraphSnapshot` 消费者零影响。

### 3.1 契约（`src/types/graph.ts`）

```ts
// GraphEdge：把 quote: string|null 改为 evidenceQuotes: string[]
//   理由：evidence_spans 本就是一对多，只留首条是信息丢失；
//   留两个字段会长期分叉，故直接替换，并同步改 GraphDetailPanel。
evidenceQuotes: string[];
evidenceCount : number;     // = evidenceQuotes.length，便于前端直接显示

// GraphNode：新增子图度数，与全库 degree 显式分开
subDegree: number;          // 在 limitGraphSize 之后按保留边实算

// GraphSnapshot：新增
chapters : { ordinal: number; title: string }[];
codeStats: { code: string; label: string; category: RelationCategory; count: number }[];
```

> ⚠️ `degree` 保持全库口径不变（它决定节点半径的既有语义不能动）；
> `subDegree` 是新增的、裁剪后的真实度数 —— **两者必须命名区分，不可混用**。

### 3.2 查询（`src/server/modules/graph/read-graph.ts`）

1. `loadEvidenceQuotes` → 改为返回 `Map<relationId, string[]>`（**保留全部**，不再 `continue` 丢后续）；
2. 新增一次 `chapters` 查询（`ordinal asc`）；
3. 新增一次 `relation_types` join 或直接用 `RELATION_TYPES` 常量算 `codeStats`；
4. `limitGraphSize` 之后遍历保留边，累加 `subDegree`。

### 3.3 连带改动

- `GraphDetailPanel.tsx`：`edge.quote` → `edge.evidenceQuotes.map(...)`，多条渲染为多个 `<blockquote>`；
- `GraphDetailPanel.test.tsx`：同步断言。

## 四、页面结构与路由（第二批）

**三视图是「同一页面内的视图切换」，不是三个路由。**
理由：共享同一份快照 + 同一个选中态（点全图节点 → 聚焦视图跟着跳；点矩阵格子 → 全图跟着高亮）。
拆三个路由会重复取数、无法共享 state —— 正是 demo 方案要避免的。

| 路由 | 内容 | 状态 |
|---|---|---|
| `/book/[bookId]` | **图谱页**（三视图合一：全图 / 聚焦 / 矩阵） | 改造现有页 |
| `/book/[bookId]/entity/[entityId]` | **人物档案页**（事迹时间线） | **新建** |

### 4.1 图谱页结构

```
<PageHeader title="人物关系图谱" breadcrumbs=... />
<GraphView snapshot>
  ├─ toolbar: 统计 + 视图切换(全图/聚焦/矩阵) + 图例过滤
  ├─ body:
  │   ├─ 主舞台（全图 Canvas / 聚焦三栏）
  │   └─ 右侧抽屉（矩阵，可收起）
  └─ 详情面板（点节点 / 点矩阵格子共用）
```

### 4.2 人物档案页

```
/book/[bookId]/entity/[entityId]/page.tsx  (RSC)
  └─ loadEntityProfile(entityId) → EntityProfile
     ├─ 头部：姓名 / 类型 / 提及密度（classifyDensity）
     ├─ 关系简述（EntityRelationBrief[]）
     └─ 事迹时间线（groupDeedsByChapter，sparse/rich 分档 + 预览截断）
```

**入口**：图谱详情面板 → 「查看人物档案」链接 → `/book/[bookId]/entity/[entityId]`。

## 五、矩阵详情卡（三视图的核心增量）

修「矩阵看不到对应角色」的关键件。

### 5.1 交互链

1. 点右侧抽屉里的矩阵格子 `(codeA, codeB)`
   - **非对角** → 列出「同时具备 codeA 与 codeB 的**人物对**」
   - **对角** → 列出「该码涉及的**所有人物对**」（默认前 20 + 「展开全部」）
2. 每张卡列：**人物对** → 关系 chips → **逐条边**（章节名 + 状态 + **多条原文**）
3. 开卡同时设 `highlightPairs` → **全图 Canvas 上对应的边高亮**

### 5.2 动态 N×N（**重要修正**）

demo 里的 **7×7 是「46 节点手工切片」的性质，不是普遍真理**。

现状问题：`TOP_CODES` 用**全库** `codes[].n` 排序取前 10，把切片内 0 条的码也带进来了。

**正确做法**：矩阵维度 = **切片内实际出现的关系码**（按切片内计数降序），动态 N×N。

> 真实页面按 degree 裁到前 300 节点，切片内可出现更多关系码 —— 因此**不可硬编码 7×7**。

### 5.3 空态（demo 已核实的三条）

- 点 `v=0` 的格子 → 不弹卡（`data-empty`，无响应）
- 0 度节点 → 「该人物在本切片中无关系记录」
- 无原文的边 → 「无原文片段（证据计数 ev=N）」

### 5.4 视觉

复用 v1 class（`.ui-card` / `.ui-badge` / `.gt-chip` / `.tl-rel-chip` / `.gl-swatch`），不新增全局 CSS；
关系配色走主题 `edgeTypeColors`（`getEdgeColorForCategory`），Canvas 内经 `--rel-*` 或已注入的 palette。

## 八、风险与陷阱

| # | 陷阱 | 正确做法 |
|---|---|---|
| 1 | `degree` 是全库口径 | 一律新增 `subDegree`，两者命名区分 |
