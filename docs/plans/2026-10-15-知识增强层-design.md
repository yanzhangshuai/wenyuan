# 知识增强层 — 架构设计（网络搜索 function call）

> 建档：2026-10-15 · 批次 66
> 定位：**图谱之外的独立层**。用网络搜索补全实体本名、补充人物简介、标注关系存疑。
> 前置阅读：`docs/架构设计与实现方案.md`（解析管线）、`docs/问题清单与后续工作.md`（缺陷清单）

---

## 一、要解决什么

| 问题 | 现状 | 本层的作用 |
|---|---|---|
| **B 类：只有称谓、本名缺失** | 儒林 428 个人物里 **82 个**零别名且 canonical 是称谓（`太祖` 没有「朱元璋」） | 搜索查证 → 补本名 |
| **人物档案内容薄** | 只有事迹时间线 + 关系（无籍贯/字号/原型） | 搜索 → 补原文没有的维度 |
| **关系无法验证** | 只能看原文证据 | 搜索 → **标注存疑，不改边** |

**一句话**：解析管线负责「从原文里读出什么」，本层负责「原文之外还能知道什么」。

---

## 二、核心约束（不可违反）

1. **解析管线零改动** —— `run.ts` 的「恰好 2 个 LLM 调用点」是成本可预测的基石，本层不得触碰。
2. **图谱只读** —— `entities` / `relationships` / `entity_mentions` **一个字节都不写**。
3. **不参与评测口径** —— 金标、变异锚点、审计脚本**不引用**本层数据。
4. **可回退** —— 删本层数据，图谱**毫发无损**。

**为什么必须独立**：搜索**结果不确定**（同一 query 不同时间结果不同），而解析管线承诺「同输入同输出」且支持 `$0 预演`。把搜索塞进管线会同时摧毁这两条。

---

## 三、架构

```
解析管线（零改动）
   ↓ 图谱落库（只读输入）
┌─────────────────────────────────────────────┐
│ 知识增强 Agent（独立进程 · 离线 · 可回退）      │
│                                              │
│ tools:                                       │
│   web_search(query)        ← function call   │
│   get_entity(book, name)   ← 读图谱（只读）    │
│   get_relationships(...)   ← 读图谱（只读）    │
│   save_knowledge(...)      ← 写独立表          │
│                                              │
│ ① 触发 ─ 按档位挑对象（非全量）                │
│ ② 检索 ─ 搜索（可缓存）                        │
│ ③ 结构化 ─ LLM 抽取成 JSON                     │
│ ④ 判决 ─ 保守：低置信不产出                    │
│ ⑤ 落库 ─ 独立表 + 来源 + 快照哈希               │
└─────────────────────────────────────────────┘
   ↓
读时叠加（UI 分区展示，不改图谱）
```

### 四个用途的定位与风险分级

| 用途 | 对图谱的作用 | 风险 | 做不做 |
|---|---|---|---|
| 补全名称 | 改 canonical（显示层） | 低 | ✅ |
| 增加简介 | 纯新增展示 | 低 | ✅ |
| **验证关系** | **只加标记，不改边** | 中 | ✅ |
| **修正关系** | — | 高 | ❌ **不做** |

**「改善关系」= 验证，不是替换。** 小说是虚构的，外部资料里的「历史真实关系」不等于书里的关系。拿外部资料改边，等于用史实覆盖文学设定。

## 四、触发策略

**判据：搜索价值 = 原文信息不足 × 外部资料存在**

| 对象 | 儒林数量 | 原文信息 | 外部资料 | 搜？ | 目的 |
|---|---|---|---|---|---|
| 称谓型实体 | 82 | 不足 | 部分有 | ✅ | 补本名 |
| `rich` 档（≥30 提及） | 23 | 充足 | **丰富** | ✅ | 补维度 |
| `moderate` 档（≥10） | 106 | 够用 | 少 | ⚠️ | 可选 |
| `sparse` 档（<10） | 743 | 不足 | **基本没有** | ❌ | — |

**反直觉点**：`rich` 档搜的不是「内容」（原文事迹最丰富），而是**原文根本没有的维度** —— 籍贯、字号、历史原型、作者意图。

---

## 五、三个真问题的解法

### ① 外部资料不是结构化关系

**解法**：外部关系**不进图谱**，只作为小传里的**一段叙述**（「马二先生是他科举仕途的引路人」），不生成新的关系边。

### ② 外部资料包含全书结局（剧透）

**解法**：**标注视角，不切片**。UI 上标为「**全书视角 · 外部资料**」，与「第 N 回」分区。不试图按回次切分外部资料（百科不按回次组织，切不出来）。

### ③ UGC 会错、无版本锚定

**解法：三重防护**
- **快照落盘**：`snapshot_hash` + `fetched_at` —— 可复现的是**快照**，不是检索
- **多源交叉**：搜 2–3 个来源，一致才采纳，冲突标 `disputed`
- **置信度分级**：`high`（多源一致）/ `medium`（单源）/ `low`（存疑，不展示）

## 六、数据模型

```
external_knowledge
  id
  book_id          -- 作品（可空 = 跨作品通用）
  subject_type     -- 'entity' | 'relationship'
  subject_key      -- 实体规范名 / 关系端点对
  field            -- canonical_name | biography | hometown
                    | courtesy_name | prototype | relation_note
  value            -- 值（文本或 JSON）
  source_urls      -- 来源数组（≥1）
  snapshot_hash    -- 抓取内容哈希
  fetched_at       -- 抓取时间
  confidence       -- high / medium / low
  disputed         -- 多源冲突标记
  created_at
```

**唯一键** `(book_id, subject_type, subject_key, field)` —— 同一对象的同一字段只保留一条，重跑即 upsert。

**为什么唯一键含 `field`**：让「补本名」与「加简介」成为**两条独立记录**，可分别重跑、分别回退。

## 七、消费方式：读时叠加

```ts
// 伪代码
const snapshot = await loadGraphSnapshot(bookId);      // 图谱（只读）
const extra    = await loadExternalKnowledge(bookId);  // 增强（独立表）
return mergeExternal(snapshot, extra);                 // 内存里合并
```

**三条铁律**：
1. 不写图谱表
2. 不参与评测
3. UI 分区（「本书信息」/「外部资料 · 全书视角」）

**回退**：`DELETE FROM external_knowledge WHERE book_id = ...` → 图谱无损；`mergeExternal` 退化为恒等函数。

## 八、执行流程

```
① 载入目标集合（补名 82 + 简介 23）
② 逐个处理
   a. 读上下文  get_entity + get_relationships
   b. 查缓存    命中且未过期 → 跳过（增量）
   c. 搜索      web_search("《儒林外史》 太祖 是谁")
   d. 抽取      LLM → 严格 JSON schema
   e. 判决      置信度 + 多源一致性
   f. 落库      upsert + snapshot_hash
③ 输出报告     处理 N / 命中 M / 冲突 K / 跳过 C
```

## 九、代码接口

| 新增 | 位置 | 性质 |
|---|---|---|
| 表定义 | `src/server/db/schema/external-knowledge.ts` | schema |
| 读侧 | `src/server/modules/graph/read-external.ts` | 只读 IO |
| 合并纯逻辑 | `src/lib/graph/external.ts` | **可测** |
| Agent | `scripts/enrich/` | **离线脚本** |
| UI | 档案页 / 详情面板**分区** | 展示 |

**关键约束**：`src/` **不得 import `scripts/`**（既有门禁钉死）⇒ 增强 Agent **结构上不可达**解析管线，不可能违反「2 个 LLM 调用点」契约。

**离线脚本模式**（沿用 `scripts/curate-work-pack.ts`）：**默认 dry-run**，不加 `--spend` 一次调用都不发；`--max-calls` 闸门超限拒跑。

## 十二、实测依据（2026-10-15 现场验证）

| 测试 | 结果 |
|---|---|
| `《儒林外史》 太祖` | 命中「《儒林外史》中多重视角下的**明太祖印象**」→ 朱元璋 ✅ |
| `儒林外史 青田先生` | 直接给出**原文注释**「青田先生: 刘基，字伯温」 ✅ |
| `儒林外史 武先生` | 给出原文「万中书道：'武先生或者还来'」+「迟衡山同武正字一对…对武书说」→ 武先生=武书 ✅ |
| `儒林外史 杜少卿 简介` | 百度百科「**杜仪**」条目 + 多篇人物分析（籍贯/字号/性格/事迹） ✅ |
| `儒林外史 匡超人 关系` | 「马二先生是**引路人/恩人**」「潘三是堕落的**加速器**」+「**马二先生本名马纯上**」 ✅ |

**结论**：补名与简介两条路径均实测可行，搜索质量足够。

## 十三、未决问题

1. **搜索源选择**：目前依赖通用搜索；是否要为「古典小说」限定到特定站点（百科/学术库）？
2. **缓存过期策略**：外部资料会变，多久刷新一次？
3. **跨作品通用的判定**：`book_id` 置空需要人工确认还是自动？
4. **简介长度**：rich 档小传多长合适？（太短无用，太长剧透）
