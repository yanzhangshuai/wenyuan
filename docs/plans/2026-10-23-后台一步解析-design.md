# 后台「一步解析」设计（导入即解析 + 实时进度）

> 日期：2026-10-23 ｜ 目标：导入书籍后自动开始解析，并在页面上看到阶段与分片进度，形态对齐 `wenyuan_v1`。

## 1. 背景与要打破的纪律

v3 现状是「Web 只入库，解析走终端」：`POST /api/admin/import` 只写
`books/chapters/paragraphs`，解析必须人工执行 `pnpm analyze <bookId>`。
这条纪律的理由是**付费长任务不进 HTTP 请求生命周期**（一次 $0.21–0.66、3–8 分钟）。

产品要求「一步执行解析」，因此必须打破它。打破的方式决定风险：

- ❌ 在 Route Handler 里 `await runPipeline()`：请求挂 5 分钟，必然超时；
- ❌ 在 Web 进程里 `void runPipeline()`（v1 的做法）：dev 热更新、服务重启都会
  让任务停在 `running`，且无法 kill；
- ✅ **独立子进程跑现有 CLI**：Web 只派活，任务生命周期与 Web 进程解耦。

## 2. 执行链路

```
POST /api/admin/import
  ├─ importBookFromText()        现有逻辑不动：写 books/chapters/paragraphs
  ├─ enqueueAnalysis(bookId)     新增：进程内串行队列
  │     └─ spawn(process.execPath, [
  │          node_modules/tsx/dist/cli.mjs,
  │          '--conditions=react-server',
  │          'scripts/analyze.ts', bookId
  │        ], { cwd: 仓库根 })
  │           stdout/stderr → logs/analyze-<runId>.log
  └─ 202 { book, analysis: { queued, position } }
```

子进程退出码决定结果：`0` → `books.status = ready`；非 `0` → `failed`，
并把日志尾部 4KB 写进 `analysis_runs.error_message`。

**为什么复用 CLI 而不新写执行器**：`scripts/analyze.ts` 已经承载了
「失败不落库」「预算超限中止」等既有语义（N20 的两个方向都处理过），
另写一份等于把控制流复制一遍，必然漂移。

**为什么用 `process.execPath`**：跨平台。Windows 下 `spawn('node')` 依赖 PATH，
生产容器里也可能没有 node 别名。

## 3. 进度模型

`analysis_runs` 增加 5 列（迁移 `0004`）：

| 列 | 类型 | 含义 |
|---|---|---|
| `stage` | `text` | `queued` / `dictionary` / `extract` / `grounding` / `vote` / `merge` / `aggregate` / `done` |
| `slices_done` | `integer not null default 0` | 已完成的 P1 分片数 |
| `slices_total` | `integer not null default 0` | 本次运行的分片总数（P0 后确定） |
| `error_message` | `text` | 失败原因（子进程非 0 / 预算超限） |
| `log_path` | `text` | 子进程日志相对路径 |

`stage` 用 `text` 而非枚举：`analysis_stage` 枚举缺 `queued`/`done`，
而 `ALTER TYPE ... ADD VALUE` 在事务内有使用限制；值域由 TS 常量
`ANALYSIS_PROGRESS_STAGES` 约束，并由契约测试钉住。

管线侧只加一个**可选回调**，不改控制流：

```ts
runPipeline({ bookId, onProgress? })
```

- P0 结束写 `stage=dictionary, total=<分片数>`；
- P1 每完成一片 `done++`（`stage=extract`）；
- P2/P4/P5/P6 各写一次 `stage`；
- 收尾写 `stage=done`。

不传 `onProgress` 时行为与现在**逐字节一致**（这是既有测试与 $0 预演的前提）。

## 4. 接口

| 方法 | 路径 | 用途 |
|---|---|---|
| `GET` | `/api/admin/books/[id]/status` | 最近一次 run 的快照：`status/stage/done/total/percent/startedAt/errorMessage` |
| `POST` | `/api/admin/books/[id]/analyze` | 手动重试（同样入队） |

两者都要求 ADMIN。前端 2s 轮询，`status !== running` 时停止。

## 5. UI

1. **导入页**：导入成功后原地展开进度卡（阶段中文名 + `已处理 x/y 片` + 百分比 +
   已用时间），跑完切成「解析完成：N 实体 / M 关系」并给「查看书籍详情」。
2. **书籍列表**：状态列 `解析中 62%`，`parsing` 时轮询。
3. **书籍详情**：进度卡；失败时显示原因与「重试解析」。

## 6. 边界与失败

| 情况 | 处理 |
|---|---|
| 同一本书已有 `running` | 不重复入队，返回 `already_running` |
| 队列长度 > 10 | 拒绝，提示稍后再试 |
| 父进程重启 | 内存队列丢失。启动时若发现 `running` 且 `started_at` 超 30 分钟，标记 `failed`（看门狗，惰性执行：读状态时判定） |
| 预算超限 | 管线抛错 → 子进程非 0 → `failed`，原因落库 |
| 取消 | 本期不做（需 pid 表 + 跨平台 kill，YAGNI） |

## 7. 测试

- **纯函数**：队列的入队/去重/串行决策（不真 spawn）；
- **契约**：`spawn` 参数（execPath / `--conditions=react-server` / 脚本路径 / cwd）、
  `ANALYSIS_PROGRESS_STAGES` 与 UI 文案表的键集合一致；
- **管线**：`onProgress` 回调被调用的次数与阶段顺序（用假回调，不连库）；
- **接口**：非 ADMIN 403、无 run 时返回 `null` 快照。

## 8. 明确不做

- 不做分布式队列 / 多 worker（单管理员场景，内存队列够用）；
- 不做取消与暂停；
- 不把解析结果流式推给前端（SSE 收益不抵复杂度，2s 轮询足够）。
