## 一、要解决什么

用户诉求原话：

> 解析时有没有设置人物简介与人物事迹？原版 wenyuan 有类似不完善功能。
> 人物简介是否可以直接接**网络简介** + **书中内容**，做成类似 book-reader-v2 那样的**百科**？

这里其实是**三个难度完全不同**的问题，必须拆开回答：

| 问题 | 难度 | 结论 |
|---|---|---|
| ① 人物**事迹**（他在哪几回做了什么） | **低** —— 数据已经在库里 | ✅ 已实现，$0 |
| ② 人物**简介**（一句话小传） | **中** —— 需 1 个 LLM 调用点 | ⏸ 待授权（付费级） |
| ③ 接**网络简介** | **低但有害** —— 引入不可复现的外部依赖 | ⚠️ 不建议；若要须物理隔离 |
| ④ **book-reader-v2 式百科** | **高** —— 产品级新方向 | 📌 可分期推进，见 §五 |

**核心判断：①②③④ 不该当成一件事。** ① 是纯工程，② 是花钱，③ 是架构污染，④ 是产品规划。

## 二、现状取证（读源码 + 实测，非推测）

### 2.1 v3 没有简介字段

`src/server/db/schema/entities.ts` 的 `entities` 表全部列：

```
id / work_id / canonical / normalized_name / type / name_type / faction_index / created_at
```

`src/types/graph.ts` 的 `GraphNode`：

```
id / name / type / factionIndex / degree / mentionCount
```

**没有任何简介、外貌、性格、事迹字段。** 这不是漏做 —— 架构文档明写首版不做：

> `docs/架构设计与实现方案.md` L4：「首版范围：垂直打通一部书…不做管理台、审核台、多书、用户体系」
> 同文 L207：「首版明确不做：审核台、用户体系、多书管理、模型配置后台、**防剧透/伴读功能**」

### 2.2 v1 `wen-yuan` 有雏形但未完成

`wen-yuan/prisma/schema.prisma` L315–385：

| 模型 | 关键字段 | 语义 |
|---|---|---|
| `Entity` | `summary`（注释「全局小传」）、`gender`、`hometown`、`globalTags`、`confidence`、`recordSource` | 跨书人物**全局档案** |
| `EntityProfile` | `localName`、`localSummary`、`officialTitle`、`localTags`、`ironyIndex`、`firstAppearanceChapterId`、`visualConfig`、`status`（`@@unique([entityId, bookId])`） | **某本书内的本地小传** |
| `ChapterBiographyVerification` | — | **逐章人工审核**流程 |

⚠️ 形态是「**档案表 + 人工审核台**」，不是自动生成。`recordSource` / `status` / `deletedAt`
这些字段都是审核向的 —— 这正是 v3 砍掉它的原因（审核台是首版明确不做的范围）。

### 2.3 v3 已有做「事迹」的全部原材料

| 表 | 提供什么 |
|---|---|
| `entity_mentions` | 段落级提及，带 `surface` / `start_offset` / `end_offset` |
| `paragraphs` | `ordinal` / `text` / `start_offset` / `end_offset`（**证据定位锚点**） |
| `chapters` | `ordinal`（**回号**，前置内容为 0）/ `title` / `raw_text` |
| `relationships` | 🆕 **自带时间轴**：`start_chapter` / `end_chapter`（null = 到书末仍成立） |
| `evidence_spans` | 关系证据的**原文引用**（`quote`） |

**关键洞察：`relationships` 的 `start_chapter` / `end_chapter` 是白送的时间语义。**
全库 966 条关系中 **328 条有终止章**，起始回分布在 **115 个不同回次** ——
即「第 N 回起与××成为主仆」这类句子可以自动生成。

### 2.4 实测数据（批次 49 现场查库，非抄记忆）

| 指标 | 儒林外史 | 红楼梦 |
|---|---|---|
| 实体总数 / 有提及 | 873 / 872 | 1004 / 1004 |
| 提及 ≥1 / ≥3 / ≥10 / ≥30 / ≥100 | 872 / 358 / 129 / 23 / 2 | 1004 / 309 / 130 / 62 / 29 |
| 人均提及 / **中位数** | 5.39 / **2.00** | 12.37 / **1.00** |
| 跨回 ≥2 / ≥5 / ≥10 / ≥20 | 318 / 76 / 18 / 1 | 333 / 149 / 83 / 46 |
| 均跨回数 | 2.04 | 4.34 |
| `evidence_spans` | 520 条 | 1003 条 |
| 有证据句的实体（并集） | 251 | 260 |

关系类型分布（全库）：朋友 335 / 主仆 230 / 父子 85 / 同僚 70 / 夫妻 65 / 师生 55 / 兄弟 54 / 母子 42 / 仇敌 25 / 同年 5。

**🚨 最重要的一个数字：提及数中位数只有 2 和 1。**
意味着**过半实体只出现一两次**，写不出任何有意义的简介。
「王胡子」「邵老丫」这类人物，能给的只有「出现在第 N 回」。

### 2.5 时间线可读性抽样

| 人物 | 提及段落 | 跨回 | 分布特征 |
|---|---|---|---|
| 杜少卿 | 114 | 17 回（31–56） | 33 回×19、37 回×18 |
| 匡超人 | 80 | **10 回**（15–56） | **15–20 回连续密集** ← 正是「匡超人传」那一段 |
| 宝玉 | 1134 | 117 回（1–120） | 全书贯穿 |

**结论：高频人物的时间线本身就是可读叙事**，不是噪声堆。匡超人这个例子最有说服力。

## 三、分层设计

「百科」不是一个字段，而是**四层**，成本与可复现性各不相同：

```
┌─ 第 4 层  百科页面（产品形态）          需产品决策
├─ 第 3 层  人物小传（一句话概述）        需 LLM（付费）· 仅对 rich 档
├─ 第 2 层  关系时间轴（谁在第几回起成为什么人）  $0 · 库内既有
└─ 第 1 层  事迹时间线（第 N 回 · 原文片段）     $0 · 库内既有   ← 已实现
```

### 第 1 层：事迹时间线（✅ 已实现）

**数据来源**：`entity_mentions` → `paragraphs` → `chapters`，
按 `(chapter.ordinal, paragraph.ordinal, start_offset)` 排序。

⚠️ 排序键必须带 `start_offset` —— 缺了它，同一段内多条提及的顺序不稳定。

**实现**：`src/server/modules/graph/read-profile.ts` 的 `loadEntityProfile()`。
**纯逻辑**：`src/lib/graph/profile.ts` 的 `groupDeedsByChapter()`（可测）。

**性质**：零 LLM、零额外成本、同输入必然同输出 → **可用 runId 锚定、可进评测口径**。

### 第 2 层：关系时间轴（$0，可用）

**数据来源**：`relationships.start_chapter` / `end_chapter` + `evidence_spans.quote`。

图谱详情面板已经在展示这个（`GraphDetailPanel.tsx` 的 `formatChapterRange`）。
百科页只需复用。

### 第 3 层：人物小传（⏸ 待授权）

**这需要 LLM** —— 归纳是模型的活。但**不能对所有实体内联**。

**必须按频次分档**（实现在 `src/lib/graph/profile.ts` 的 `classifyDensity`）：

| 档位 | 判据（提及段落数） | 儒林 | 红楼 | 策略 |
|---|---|---|---|---|
| `rich` | ≥ 30 | 23 | 62 | ✅ 值得 LLM 归纳 |
| `moderate` | ≥ 10 | 106 | 68 | ⚠️ 可展示时间线；概述需谨慎 |
| `sparse` | < 10 | **743** | **874** | ❌ 只给原文落点，**不编造** |

**🚨 分档是承重设计而不是优化**：不分档就会对 743+874 个长尾实体生成空洞内容。

**实现方式（建议）**：仿照 `scripts/curate-work-pack.ts` 的**离线脚本**模式：

- **默认 dry-run**，不加 `--spend` 一次调用都不发；
- `--max-calls` 闸门，计划调用数超限直接拒跑；
- `src/` 不得 import `scripts/`（已有门禁钉住）→ 离线调用点**结构上不可达**，
  因此不违反「流水线恰好 2 个 LLM 调用点」的 C3 契约。

⚠️ **一旦跑了并落库，就是「库与代码不一致」**（铁律③），且按铁律④须先 dump run 级证据。

### 第 4 层：百科页面（📌 产品决策）

见 §五。

## 四、为什么反对「接网络简介」

不是「做不到」，是**投入产出比极差**：

1. **目标人群错配**：需要网络简介的是主要人物（宝玉、黛玉），
   而这类人**恰恰是书上内容最丰富、最不需要外援的**。
   真正需要帮助的是长尾（743 个 sparse 实体），而**网上根本没有他们的简介**。

2. **口径打架**：网上简介**普遍剧透**（「贾宝玉最终出家」），
   而图谱按回次切片。两者拼在一起会破坏「按阅读进度」的语义。

3. **污染可复现性**：网搜**不可回放**。
   本项目整套评测体系（金标、变异、审计、`_wb_gold_attest`）都建立在
   「同输入同输出」上；引入联网检索等于在流水线外挂一个**无法用 runId 锚定**的环节。

4. **成本不再线性**：extract 占成本 93.7%/97.7% 是「成本可预测」的前提。
   外挂联网检索打破这个承诺。

### 若确实要做

**必须物理隔离**：

- 单独一张表（如 `external_summaries`），带 `source_url` + `fetched_at` + `version`；
- **永不参与任何评测口径**（不进金标、不进变异锚点）；
- UI 上明确分区（「本书信息」/「外部资料」），视觉上可区分；
- 抓取走离线脚本，结果快照落盘（可复现的是**快照**，不是检索）。

## 五、book-reader-v2 式百科：分期路线

「百科」隐含的功能远超「加一个字段」：

| 能力 | 现状 | 缺口 |
|---|---|---|
| 人物卡（名字/类型/别名/统计） | 已有（详情面板） | 需扩展为独立页面 |
| 事迹时间线 | ✅ **本批已实现** | 接 UI |
| 关系时间轴 | ✅ 已有（详情面板） | 复用 |
| 关系网络可视化 | ✅ 已有（`ForceGraphCanvas`） | 复用 |
| 点人物跳原文 | ⚠️ 有段落坐标，未接 | 需原文渲染页 |
| **按回次防剧透** | ❌ 无 | **架构文档明写首版不做** |
| 交叉引用（A→B→C 跳转） | ⚠️ 详情面板有雏形 | 需路由 |

**分期建议**：

- **第一期（$0，可立即做）**：人物档案页 = 第 1 层 + 第 2 层 + 已有关系数据。
  **不含 LLM、不含防剧透、不含联网** → 不碰任何门禁承诺。
- **第二期（付费）**：对 `rich` 档实体加小传（第 3 层）。
- **第三期（产品）**：原文渲染 + 防剧透 + 交叉引用。

**🚨 不要在第一期就把「防剧透」列进验收标准** —— 它是架构文档明写首版不做的东西，
会立刻把范围炸开。

🆕 新增变异套件 `_wb_mutation_profile.py`（第十轮，5 条变异）：

- P1 分组判据改成「回号相等即复用」→ 不同回错误并入同组
- P2 「与上一组同回」改成「回号连续」→ 缺口被补齐

## 七、可交互原型

`_wb_demo/人物百科原型.html`（独立文件，双击即开，数据已内联）：

- 左侧：两部作品 × 三档实体（rich / moderate / sparse）共 14 个样例；
- 右侧：档案头（类型/提及数/跨回/首末回/别名）+ 事迹时间线 + 关系表；
- 全部内容由**库内数据确定性生成**，含 0 次模型调用；
- sparse 档显式展示「信息不足以生成可靠概述，只呈现原文落点，不编造小传」的提示。
