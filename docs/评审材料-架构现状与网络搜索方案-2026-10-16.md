## 〇、背景一句话

**AI 小说人物关系图谱构建器**。输入一本中文古典小说的全文（txt），输出「人物实体 + 别名 + 关系边」的知识图谱，供网页端可视化浏览。

立项时确定的两个核心痛点：**token 成本过高**、**解析准确率过低**。目标是「用确定性工序替代 prompt 技巧」来同时降本与提准。

当前已跑通两部书：《儒林外史》（57 回，约 995 KB）、《红楼梦》（120 回，约 2.57 MB）。

## 一、当前架构

### 1.1 总体形态：「LLM 当算子」的固定流水线，**不是 agent**

这是本项目的核心架构选择，也是理解后面所有设计的前提：

- **无 tool calling、无自主循环、无 agent 编排**
- **恰好 2 个 LLM 调用点**（写死在 `run.ts` 中）：
  - `dictionary`（P0）：**1 次/本**
  - `extract`（P1）：**1 次/片**
- 其余所有阶段都是**确定性纯代码**（0 LLM）
- 因此**成本线性可预测**：调用次数 ≈ 1 + 片数，可以在跑之前精确算出来

**为什么坚持这个形态**：立项时分析过 v1/v2 两个失败版本，结论是「准确率不靠 prompt 技巧，靠确定性工序」。把 LLM 限制为「算子」而非「决策者」，才能让每个环节可测、可复现。

### 1.2 七个阶段

| 阶段 | 做什么 | LLM | 成本占比 |
|---|---|---|---|
| **P0 预扫描词典** | 全书段落 → jieba 分词 + n-gram + 后缀规则（先生/老爷/知县/府/县…）统计候选频次 → 小模型分类成**锚定白名单** | ✓ 1 次/本 | 小 |
| **P1 分片提取** | 每片正文 → 候选 JSON（人物 / 别名 / 关系 / 证据引文） | ✓ 1 次/片 | **93.7%–97.7%** |
| **P2 grounding** | 候选名 → 全库 corpus 字面匹配，**无字面证据的候选直接剔除** | ✗ | 0 |
| **实体闸门（8 步）** | 列举式规范名 → 泛称 → 姓氏+氏 → 尊称 → 官职 → 身份/职业 → 收 | ✗ | 0 |
| **P4 类型投票** | 同一实体对在多片中的类型做多数投票，tie-break 保守 | ✗ | 0 |
| **P5 归并 / 别名** | Union-Find（按 normalized）+ 不安全别名黑名单 + **canonical 决策** | ✗ | 0 |
| **P6 关系聚合** | 关系有效期契约 `OBSERVE/BEGIN/END` → 聚合为 `INSERT/EXTEND/CLOSE` | ✗ | 0 |

> 注：立项时设计过 **P3 独立二审**（机制上读不到一审结果，数据路径隔离），但实施中发现收益不显，**已删除**。

### 1.3 三层题材包（genre pack）

```
通用包（default）
  └── 古典包（classical）：中式称谓、官职、姓氏+氏 等词表
        └── 具体书包：书名号内作品名等
```

**已验证**：加《红楼梦》包时**未改任何控制流**，说明接口是充分的。

### 1.4 关键工程机制

- **分片**：字数驱动滑动窗口，3000–4000 字/片，重叠 300–400 字，边界优先段落；章内 >8000 字再切
- **结构化输出**：Zod → JSON Schema → `response_format`；截断走 `repair-truncated-json`（去围栏 / 补括号）
- **重试按错误类别分流**：`output_not_json` / `truncated` → **不重试**（走 repair 或切更小的片）；`rate_limit` / `5xx` / `timeout` → 指数退避 ≤2 次
- **证据定位**：模型只回 `quote`，服务端做**唯一匹配**落坐标，多义即判 `INVALID`
- **归并防丢**：所有名字经 `normalizeName()`（去空白 / 全角、大小写折叠）写入 `normalized_*` 列并建唯一索引；**归并只改外键，永不靠名字回填**（v1 的 mentions 丢失根因就是靠名字回填）
- **关系有效期**：支持「师徒反目、夫妻离散」的时序，未结束的关系 `end_chapter = null`

### 1.5 数据模型（PostgreSQL + Drizzle，12 张表）

核心表：`books` / `chapters` / `paragraphs` / `entities` / `entity_aliases` / `entity_mentions` / `relationships` / `relation_types` / `evidence_spans` / `analysis_runs` / `analysis_calls` / `analysis_issues`。

- 图谱是**邻接表 + 递归 CTE**（不用 Neo4j）
- `analysis_runs` 冻结快照（model / prompt_version / skill_snapshot）→ 每个 run 可追溯
- `entities` / `relationships` **无 runId** → 历史图谱不可回读（重跑即覆盖）

### 1.6 评测体系

- **金标**：**3 个切片** —— 儒林外史 1-1（第 1 回）、儒林外史 1-3（前 3 回）、红楼梦 1-3（前 3 回）
- **指标**：微平均 F1
  - 实体 F1 = 名字集合（canonical ∪ aliases，normalized）命中 **且类型一致**
  - 关系 F1 = typeCode + 两端命中，对称码允许方向互换
- **门禁**：`entityF1 ≥ 0.74`
- **辅助指标**：grounding 通过率、跨章实体一致性

### 2.4 已发现的缺陷

#### ✅ 已修：A 类「称谓被当成规范名」

**根因**（定位到具体一行）：`merge.ts` 的 `pickCanonicalKey` **只按出现频次选规范名**，而书里对人物的**称谓**出现次数**必然多于本名** → 规范名落成敬称。

```js
// 修复前
/** 选择规范名：优先出现次数多者；次数相同取较短者（短名更接近本名而非敬称）。 */
if (current > bestFrequency || (current === bestFrequency && key.length < best.length))
// ↑ 注释里「短名更接近本名」只在同频次时才生效，而频次优先级更高
```

**实测**：儒林 429 个人物里 **18 个**如此，且**本名已经在别名里**。例如 `马二先生`（别名含「马纯上」「马静」）、`卫先生`（别名含「卫体善」）、`李老爷`（别名含「李梦阳」）。

**修法**：新增 `name-form.ts`，导出两个纯函数 —— `isHonorificForm`（判称谓形式）与 `isProperNameForm`（**正向**判「像本名」）；`pickCanonicalKey` 改为**先按形态分层**（专名层优先），候选全是称谓时回退原逻辑。

**关键教训**：**「不是称谓」≠「是本名」**。只做排除会把 `才女`、`老二`、`吴王`、`小侄` 这类**既非称谓也非本名**的写法选出来，把规范名**改得更差**。做 $0 预演时第一版会改 39 个实体（大量误伤），迭代三轮收紧到 25 个。

#### ❌ 未修：B 类「本名完全缺失」

原文**只给称谓**，本名根本不在书里。例如 `太祖`（书中出现 6 次，**「朱元璋」三个字一次都没出现**）、`周老爷`、`三公子`。

| 作品 | 数量 |
|---|---|
| 儒林外史 | **74** |
| 红楼梦 | **34** |

其中约 10 个是**历史人物**（`太祖→朱元璋`、`成祖→朱棣`、`青田先生→刘基`），本名可从常识补；其余是原文信息缺失。

#### ❌ 未修：C 类「同一人被拆成多个实体」

例如《儒林外史》的 `严大位` / `严致中` / `严贡生` 实为一人（严大位字致中，人称严贡生），但三者**别名互不交叉**，规则抓不到。

**试过的检测手段与结果**：

| 手段 | 结果 |
|---|---|
| 别名撞规范名 | 返回 **0 组** |
| 同姓 + 同段落共现 | 返回 **12 组候选**，但抽查 4 对里 3 对是**亲属关系**（`秦老⇄秦大汉` 是父子、`杜娘子⇄杜少卿` 是夫妻、`匡太公⇄匡大` 是父子），只有 `武先生⇄武书` 确认同一人 |
| 编辑距离 = 1 检「同一人」 | 等长 + 距离 1 得到 **110 组**，逐条看下来「万中书⇄秦中书」「周进⇄范进」「匡大⇄王大」**都是不同的人**；真正的错字分裂只占约 10 组 → **噪音率 >90%，不可作结论** |

**结论**：C 类问题**基于字符串相似度的规则给不出可信数字**，需要语义理解。

#### ❌ 未修：错字 / 异体分裂

人工确认约 10 组：`庄濯江⇄庄耀江`、`高青丘⇄高青邱`、`乌龙潭⇄乌龙谭`、`燕子矶⇄燕子矾`、`莺脰湖⇄莺豆湖`。

### 2.5 本轮新量出的「不确定性」分布

用五个**确定性检测器**（只依赖图谱自身）量出来的：

| 类型 | 检测方式 | 儒林外史 | 红楼梦 |
|---|---|---|---|
| ① 本名缺失 | 称谓型 canonical + 零别名 | **74** | **34** |
| ② 同人歧义 | 同姓存在「像本名」的实体 | **61** | **27** |
| ③ 类型存疑 | 类型与词形矛盾 | **15**（⚠️ 误报多，见下） | **3** |
| ④ 同段落共现 | 同段落共现 | **12** | — |
| ⑤ 关系脆弱 | **只有一条原文证据** | **274 / 349 = 78.5%** | **235 / 388 = 60.6%** |

⚠️ **③ 的检测器本身有洞**：初版用「地名后缀表」（府/县/州/江/山/亭…）判类型矛盾，结果把 `庄濯江`、`迟衡山`、`景兰江`、`娄瑟亭` 全误判为地名 —— 因为**「江 / 山 / 亭」既是地名词尾，也是人名常用字**。真正的疑似只有 `老父台`（父台 = 对地方官的尊称）、`范学台`（学台 = 学政）这类**官职词被当人名**。

> **含义**：检测器本身也需要被验证。这与「编辑距离在中文人名上失效」是同一类错误 —— **拿通用规则去量中文人名**。

## 三、我想要的「网络搜索增强」方案

### 3.1 问题定性：系统缺一根支柱

当前系统**只认原文，没有外部参照系**。后果：

1. 一个「只有称谓」的实体（`太祖`）和一个「名字确定、类型可疑」的实体，在图谱里**长得一模一样** —— 系统无法对自己的输出表态
2. `太祖` 被当成一个正常名字存下来，系统**不知道**这是个不完整指代
3. 关系抽错时只能靠原文自证，而它自己只有一份材料 —— **78.5% 的关系只有一条证据**
4. 系统**被迫给答案**：把「太祖」当成完整实体，而不是标记「本名未确定」

```
① 抽取（神经）    LLM 从原文读知识            ← 已有
② 校验（符号）    确定性工序过滤 / 投票 / 归并   ← 已有
③ 校验（外部）    搜索获取外部知识，交叉验证     ← 缺这一根
```

**核心目标**：**系统要能意识到自己的不确定** —— 不是「补全缺失」，而是「知道自己的边界在哪」。

### 3.2 核心设计：检测 $0 / 判定付费

**分界线**：

```
检测 Detection            判定 Resolution
只依赖图谱自身             需要图谱之外的信息
确定性 · $0 · 可预演       不确定 · 需搜索 · 不可预演
→ 进 src/（可测）          → 进 Agent（离线、可缓存）
```

§2.5 的五类检测**全部只依赖图谱自身**（实体名、别名、提及段落、证据片段），所以可以**整体进 `src/`、可库内精确重放**（预测表 + 跑完对账），**不需要等搜索层就绪**。

### 3.3 不确定性的四类来源 + 可操作行动

| 来源 | 本质 | 触发条件 | 行动 | 终态 |
|---|---|---|---|---|
| ① 原文信息不足 | **不知道** | 称谓型 canonical 且零别名 | 搜索补本名 | `resolved` / `unresolvable` |
| ② 抽取可能出错 | **可能错** | 类型与词形矛盾 | 外部校验 | `corrected` / `confirmed` |
| ③ 归并可能出错 | **可能错** | 同段落共现的疑似同一人 | 搜索验证 | `merged` / `distinct` |
| ④ 外部不可得 | **不可知** | 搜索无结果 | **不猜，标记** | `unresolvable`（终态） |

**两条设计原则**：

- **「不知道」和「错了」是两件事** —— 前者该**标记**不该猜，后者该**验证**可修正
- **必须能表达终态 `unresolvable`** —— 系统必须能说「我尽力了，但确实不知道」，而不是被迫给一个答案

### 3.4 架构：独立 Agent，与解析管线解耦

```
解析管线（零改动）
   ↓ 图谱落库（图谱是只读输入）
┌────────────────────────────────────────┐
│ 知识增强 Agent（独立 · 离线 · 可回退）    │
│  tools: web_search / get_entity /       │
│         get_relationships / save_knowledge │
│  ① 触发 ─ 按档位挑选对象（不是全量）       │
│  ② 检索 ─ 搜索 function call（可缓存）     │
│  ③ 结构化 ─ LLM 抽取成 JSON               │
│  ④ 判决 ─ 保守：低置信不产出               │
│  ⑤ 落库 ─ 独立表 + 来源 URL + 快照哈希     │
└────────────────────────────────────────┘
   ↓ 读时叠加（UI 分区展示，不改图谱）
```

**为什么必须独立**：

1. 解析管线的「**成本线性可预测**」是产品基石（恰好 2 个 LLM 调用点）。搜索**结果不确定**，塞进去会让成本与结果都不可预测
2. **$0 预演能力依赖「不碰 P1 输出」**。搜索一旦进管线，预演能力直接失效
3. **反向依赖也是错的** —— 增强层**只读**图谱、**只写**自己的表。删掉整个增强层，图谱**毫发无损**

### 3.5 触发策略（成本与收益的分配）

**搜索的价值 = 原文信息不足 × 外部资料存在**。

| 对象 | 数量（儒林） | 原文信息 | 外部资料 | 搜？ | 目的 |
|---|---|---|---|---|---|
| 称谓型实体 | 74 | 不足 | 部分有 | ✅ | **补本名** |
| `rich` 档（≥30 提及） | 23 | 充足 | **丰富** | ✅ | **补原文没有的维度** |
| `moderate` 档（≥10） | 106 | 够用 | 少 | ⚠️ | 可选 |
| `sparse` 档（<10） | 743 | 不足 | **基本没有** | ❌ | — |

**一个反直觉的点**：`rich` 档搜索**不是**为了「补内容」（原文事迹最丰富），而是为了补**原文根本没有的维度** —— **籍贯、字号、历史原型、作者意图**。

**所以「全量逐实体搜索」是错的** —— 大部分会返回空，收益递减到零。

### 3.6 闭环：判定结果的三条路径

| 路径 | 内容 | 成本 | 风险 |
|---|---|---|---|
| **① 回图谱** | 判定结果作为独立元数据**读时叠加**，不写 `entities` / `relationships` | **$0** | 无（删表即还原） |
| **② 回题材包** | 外部资料显示某称谓/后缀**从未被识别** → 词表有洞 → 补词 | ⚠️ **付费** | **打破 $0 可预演** |
| **③ 回评测** | 「**不确定性覆盖率**」成为一项指标 | **$0** | 无 |

⚠️ **路径 ② 是唯一危险的一条**：它会改 P1 的输入 → **直接打破 $0 可预演**。所以**不能自动执行** —— 只能产出「**待补词候选表**」，人工确认后走**显式记账**的付费重跑。

### 3.7 数据模型

**核心决策：检测不落库，判定落库。**

| | 存哪 | 理由 |
|---|---|---|
| **检测结果**（5 类标记） | **不落库**，读时算 | 是图谱的**确定性派生**；落库只会引入 stale |
| **判定结果**（外部知识） | 独立表 `external_knowledge` | 有成本、需缓存、需可复核 |

**为什么不把检测结果落库**：落库就要挂进 `persistGraph` → 属**导入期代码** → 触发项目里「**改导入期代码必须重导**」的连锁后果（级联清空该作品全部 run、全部 entities/relationships）。**读时算是唯一不碰导入期的做法。**

```sql
create table external_knowledge (
  id            uuid primary key default gen_random_uuid(),
  book_id       uuid references books(id),        -- null = 跨作品通用
  subject_type  text not null,                    -- 'entity' | 'relationship'
  subject_key   text not null,                    -- 规范名 / 端点对
  field         text not null,                    -- canonical_name | biography | hometown
                                                  -- | courtesy_name | prototype | relation_note
  value         text,
  resolution    text not null,                    -- 'resolved' | 'disputed' | 'unresolvable'
  source_urls   text[] not null default '{}',
  snapshot_hash text,
  confidence    text not null,                    -- 'high' | 'medium' | 'low' | 'none'
  fetched_at    timestamptz not null,
  created_at    timestamptz not null default now()
);
```

两个设计要点：

- 唯一键含 `field` → 「补名」与「简介」是**两条独立记录**，可分别重跑、分别回退
- **「查过了，查不到」也要落库**（`resolution = 'unresolvable'`）—— 否则每次重跑都要重查

**消费方式**：读时叠加

```ts
const snapshot    = await loadGraphSnapshot(bookId);
const uncertainty = computeUncertainty(snapshot);        // $0 派生 · 纯函数
const external    = await loadExternalKnowledge(bookId); // 独立表
// UI 分区展示，不合并进 snapshot
```

**三条铁律**：不写图谱表 · 不进评测口径 · UI 分区。

### 3.8 外部知识的定位：**证伪，不证真**

| | 原文 | 模型参数知识 | 外部检索 |
|---|---|---|---|
| 跨过信息边界 | ✗ | ✓ | ✓ |
| **有出处可复核** | ✓ | ✗ | ✓ |
| 可复现 | ✓ | ✗ | ✗ |
| 错误面 | 小（误读） | **大（幻觉，且查不出来）** | 中（UGC 会错，但看得见） |
| 成本 | 已付 | 免费 | 免费/低 |

**参数知识与外部检索都能跨过边界，但只有外部检索留下了出处。** 搜索比「让模型自己回忆」强，**不是因为搜得更准，而是因为错了能追**。

**根本局限**：外部资料**擅长证伪，不擅长证真**。

- 能说「这名字查不到 → 可疑」✅
- 能说「百科写的是另一个名字 → 可能错了」✅
- **不能**说「这条关系对」❌ —— 百科讲的是**历史人物**，书里是**文学形象**；一致不等于书里就是这么写的

**所以外部知识只产出「疑点」与「置信度」，不产出「事实」** —— 它**标注，不改写**。

### 3.9 分期

| 期 | 内容 | 成本 |
|---|---|---|
| **一期** | 检测能力（纯函数 + 读侧）+ 覆盖率指标 | **$0** |
| **二期** | UI 分区展示（标出「不确定」） | **$0** |
| **三期** | 搜索 Agent + `external_knowledge` 表（判定） | 搜索 $0 + 抽取 ≈$0.05 |
| **四期** | 路径② 词表补洞 | ⚠️ 付费 + 显式记账 |

**前置条件**：**先补尺子** —— 现有金标只覆盖前几回，而规范名问题集中在中后段（`马二先生` 在第 13–15 回）。**不扩金标就测不出效果**，即使搜索层修对了读数也不会动。

### 3.10 明确不做（YAGNI）

- 外部知识**不改写**图谱结构（只标注）
- 外部关系**不生成边**（小说虚构，外部资料不能覆盖文学设定）
- **不自动改**题材包词表（须人工确认 + 显式记账）
- **不做**全量逐实体搜索（`sparse` 档 743 个网上没有资料）

## 四、请评审回答的问题

请**重点质疑**以下判断。如果哪条在方法论上站不住，请直接说。

1. **「检测 $0 / 判定付费」这条分界是否成立？**
   我们的论据是：检测只依赖图谱自身 → 确定性 → 可 $0 预演。但有没有可能某些「检测」本质上也需要外部知识（即这条线画错了位置）？

2. **「外部知识只标注、不改写」是否过于保守？**
   好处是可回退、不污染图谱。但风险是：**产品上看起来什么都没变**（用户看到的还是「太祖」），那这个能力的价值在哪？

3. **用「外部资料证伪」来给不确定性排序，方法论上可靠吗？**
   我们担心一个系统性偏差：**网上有资料的人物 = 主要人物 = 本来抽得最好的那批**。而真正需要帮助的长尾（`sparse` 档 743 个）**恰恰网上没有资料**。如果是这样，这套外部校验**只对已经做对的部分有用**，是不是一种「幸存者偏差」？

4. **「78.5% 的关系只有一条原文证据」—— 这是普遍现象还是我们的抽取质量问题？**
   我们的解读是「脆弱而非错误」。但如果一个更好的抽取器本应找到多条证据，那这个数字反映的是**召回不足**，而不是「原文如此」。

5. **金标只覆盖前几回（3 个切片）—— 如何设计才能测出中后段的问题？**
   扩金标是人力瓶颈。有没有更省力的替代方案（如自动构造伪金标、跨书迁移）？

6. **`type_suspect` 检测器的正确形态是什么？**
   `PLACE_SUFFIX` 已被证伪（`江/山/亭` 是人名常用字）。中文人名的「类型与词形矛盾」该怎么做才可靠？

7. **架构上，把外部校验做成独立 Agent 是否是对的？还是应该进管线？**
   我们的理由是「保护成本可预测性与 $0 预演」。但独立带来的代价是：**它是离线的、不是实时的**，新导入一本书后不会自动校验。

8. **成本模型是否合理？**
   估算：74 个补名 + 23 个简介 ≈ 97 次搜索 + 97 次 LLM 抽取 ≈ $0.05–0.15（一次性）。这个量级与「一次性知识获取」的定位是否匹配？

9. **有没有我们完全没想到的方向？**
   特别是：如果目标只是「让系统知道自己哪里不确定」，**是否根本不需要网络搜索**？（例如纯靠「图谱内部一致性」能否推出不确定性？）
